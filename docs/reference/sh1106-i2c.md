# SH1106 I2C map

The SH1106 is an OLED segment/common driver: 132 segment outputs, 64 commons, 132 × 64 bits of
display RAM and an on-chip DC-DC converter. It is the controller on the 1.3" 128 × 64 panel this
machine is built with — the module bonds 128 of the 132 segment outputs to the glass, and the RAM
columns at either end are never shown.

Every opcode, argument bit and power-on reset value below is the part's, quoted from the Sino Wealth
SH1106 datasheet (V0.1). Where the firmware's driver does something narrower than the part allows,
that is said so, in "As this tree drives it".

## The bus

The part is an I2C slave at up to 400 kHz. The slave address is 0111100 or 0111101, picked by the
SA0 pad; a module straps SA0, and nearly every 1.3" panel answers at `0x3C` (`0x3D` when the strap
pulls it high).

After the address byte comes a control byte: continuation (`Co`, bit 7), data or command (`D/C#`,
bit 6), and six zero bits.

| Co | D/C# | Control byte | What follows |
| --- | --- | --- | --- |
| 0 | 0 | `0x00` | command bytes, to the end of the transfer |
| 0 | 1 | `0x40` | display RAM bytes, to the end of the transfer |
| 1 | 0 | `0x80` | one command byte, then another control byte |
| 1 | 1 | `0xC0` | one RAM byte, then another control byte |

`Co` clear marks the last control byte of a transfer, which is why a command burst is one control
byte and one transmitted buffer. The part takes all four forms; the firmware only ever sends `0x00`
and `0x40`, one control byte per transmission.

The RAM is not readable over this interface — the datasheet states plainly that no display data can
be read via the serial interface. A read transfer returns the status byte instead: bit 7 busy, bit 6
display off (high means off, the opposite sense to the command's argument). Both are uninteresting
to a driver that sends the delays below and writes only.

## The address space

The RAM is 132 columns by 8 pages. A page is eight rows; one RAM byte is one column of one page, and
within a byte bit 0 is the top row of the page and bit 7 the bottom.

There is page addressing and nothing else: no memory-addressing-mode instruction, no column or page
window registers. A window is opened by writing the page, then both halves of the column address,
and RAM bytes then walk the column counter up by one each. The counter stops at column 132 and the
page does not advance, so a driver re-opens the window for each page it writes.

Column addresses run 0–131, so the last column is `0x83`: a low-nibble byte of `0x03` and a
high-nibble byte of `0x18`. On a 128-wide module the glass begins at RAM column 2 — pixel column `x`
is written at RAM column `x + 2`. Offsets of 0 and 2 both exist among 1.3" modules, so the offset
belongs to the module rather than to the controller, and a display shifted by a column or two is
answering from a different offset rather than being mis-addressed.

## The commands

| Opcode | Command | Bytes | Argument | POR |
| --- | --- | --- | --- | --- |
| `0x00`–`0x0F` | set lower column address | 1 | bits 3:0 of the column | `0x00` |
| `0x10`–`0x1F` | set higher column address | 1 | bits 7:4 of the column | `0x10` |
| `0x30`–`0x33` | pump voltage | 1 | `0x30` 7.4 V, `0x31` 8.0 V, `0x32` 8.4 V, `0x33` 9.0 V | `0x30` |
| `0x40`–`0x7F` | display start line | 1 | line 0–63 | `0x40` |
| `0x81` | contrast | 2 | `0x00`–`0xFF`, 256 steps | `0x80` |
| `0xA0`/`0xA1` | segment remap | 1 | `0` column 0 to SEG0, `1` column 131 to SEG0 | `0xA0` |
| `0xA4`/`0xA5` | entire display off / on | 1 | `0` follows RAM, `1` ignores it | `0xA4` |
| `0xA6`/`0xA7` | normal / inverse | 1 | `0` a set bit lights a pixel | `0xA6` |
| `0xA8` | multiplex ratio | 2 | 1–64 rows | `0x3F` |
| `0xAD` | DC-DC mode set | 2 | `0x8A` off, `0x8B` on | `0x8B` |
| `0xAE`/`0xAF` | display off / on | 1 | `0` off, `1` on | `0xAE` |
| `0xB0`–`0xB7` | page address | 1 | page 0–7 | `0xB0` |
| `0xC0`/`0xC8` | COM scan direction | 1 | `0` COM0 first, `1` COM63 first | `0xC0` |
| `0xD3` | display offset | 2 | 0–63 rows | `0x00` |
| `0xD5` | clock divide and oscillator | 2 | low nibble divide ratio − 1, high nibble frequency trim | `0x50` |
| `0xD9` | pre-charge and discharge | 2 | bits 3:0 pre-charge, bits 7:4 discharge, 1–15 DCLK each, 0 invalid | `0x22` |
| `0xDA` | COM pins | 2 | `0x02` sequential, `0x12` alternative | `0x12` |
| `0xDB` | VCOM deselect level | 2 | `VCOM = (0.430 + A × 0.006415) × VREF` | `0x35` |
| `0xE0` | read-modify-write start | 1 | — | — |
| `0xE3` | no operation | 1 | — | — |
| `0xEE` | read-modify-write end | 1 | — | — |
| `D/C# = 1` | write display data | — | one RAM byte per byte sent | — |

The datasheet numbers 24 commands in all: the ones above and the two reads described under the bus.
The ones it does not list are not to be sent, and a byte that is not one of them is undefined
behaviour rather than a no-op.

Two arguments deserve their bit layout spelled out. `0xD5` splits the divide ratio into the low
nibble, where the value is the ratio minus one, so `0x0` is a divide of 1, and the oscillator trim
into the high nibble, where `0x5` is the nominal frequency and every step beyond it is 5% — `0x80`
and above run the panel about 15% fast. `0xDB` maps `0x00` to 0.430 × VREF and climbs 0.006415 VREF
per step to 0.770 × VREF at `0x35`, the reset level; `0x40` and above all clamp to 1.0 × VREF, which
is where a panel that looks over-driven has been left.

The multiplex ratio must match the glass: `0x3F` for 64 rows, `0x1F` for 32. A ratio below the
height leaves the bottom rows undriven, and one above it makes the COM outputs walk off the end of
the panel.

## The sequences

Power-up, as the datasheet orders it: hold RES low while VDD1 and VDD2 come up, release it, then
send the setup commands, clear the RAM — the content is undefined after reset — turn the DC-DC on,
wait about 100 ms, and only then send `0xAF`. The wait is the DC-DC reaching its voltage, not a
command latency; the datasheet also asks for about 150 ms after display on before sending data.

There is no reset pin on the common module's four-wire header, and none is needed: every value in
the POR column is what the part holds after its own reset, so a driver that writes the whole
configuration gets the same state either way.

As this tree drives it, `Sh1106Device::begin` sends one command burst and then display on:

| Bytes | Command | What it sets |
| --- | --- | --- |
| `0xAE` | display off | nothing shows while the panel is configured |
| `0xD5 0x80` | clock divide | divide 1, oscillator about 15% fast |
| `0xA8 0x3F` | multiplex ratio | 64 rows |
| `0xD3 0x00` | display offset | COM0 is the first RAM line |
| `0x40` | start line | line 0 at the top |
| `0x8B` | DC-DC on | the data byte alone; the part's reset already has the DC-DC on, so no `0xAD` mode set |
| `0xA1` | segment remap | column 131 to SEG0, behind the 2-column offset |
| `0xC8` | COM scan | COM63 first |
| `0xDA 0x12` | COM pins | alternative layout |
| `0x81 0xFF` | contrast | 255 of 256 |
| `0xD9 0x1F` | pre-charge and discharge | pre-charge 15, discharge 1 DCLK |
| `0xDB 0x40` | VCOM deselect | clamped to 1.0 × VREF |
| `0x33` | pump voltage | 9.0 V |
| `0xA6` | normal display | a set bit lights a pixel |
| `0x20 0x10` | — | `0x20` is not an SH1106 instruction, and `0x10` sets the column high nibble to 1, which the first window replaces |
| `0xA4` | follows RAM | the frame, not all-on |
| `0xAF` | display on | after a 100 ms delay |

A flush then writes one window per page — `0xB0 + page`, `0x10 | ((x + 2) >> 4)` and
`(x + 2) & 0x0F` — and follows it with a `0x40` control byte and the page's column bytes. The window
holds across the several transmissions a long run of columns takes, because the column counter
advances with the RAM writes and no command intervenes.

## Against the SSD1306

The two parts share most of their opcodes, which is why a driver written for one nearly works on the
other, and differ where a driver would notice.

| | SH1106 | SSD1306 |
| --- | --- | --- |
| RAM | 132 × 64 bits | 128 × 64 bits |
| Addressing | page only | page, horizontal, vertical |
| Column and page windows | none: `0x00`–`0x1F` and `0xB0`–`0xB7` | `0x21` and `0x22`, in horizontal and vertical modes |
| Hardware scroll | none; move the start line | `0x26`/`0x27`/`0x29`/`0x2A`, `0x2E`/`0x2F`, `0xA3` |
| Supply for the panel | DC-DC, `0xAD` then `0x8A`/`0x8B`, voltage at `0x30`–`0x33` | charge pump, `0x8D` then `0x14` |
| Oscillator reset | `0x50`: trim of `0x5` is nominal | `0x80`: trim of `0x8` is nominal |
| VCOM deselect | 0.430–1.0 × VREF over the byte, `0x35` at reset | three steps, `0x00`, `0x20`, `0x30` |
| Visible columns | 128 of 132, offset 2 on the common module | all 128 |

which it is, telling them apart is [panel-identification.md](./panel-identification.md).
